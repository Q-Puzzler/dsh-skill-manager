# Client-to-host calls over plain webServer routes, not the Typert Remote gateway

The dsh API Gateway (`@Remote` methods, `ctx.remote.<namespace>` client calls) generates its client-side contributions through a monorepo-owned build pipeline, and the client assembly (`@deepseek-ai/dsh-api-remotes`) explicitly mounts the `/remote` subpaths of selected in-repo business packages. An external plugin cannot join that assembly, so the Remote path is effectively unavailable to us.

The SkillManager host service therefore exposes plain HTTP routes registered on `ctx.webServer` under a plugin-unique prefix, and the settings card calls them with ordinary `fetch`. The shared `/api` bridge and the `/plugins/<id>/client.js` bundle route are owned by dsh internals; our prefix avoids both.

Related external-plugin constraints discovered in the same doc review, recorded here so they are not rediscovered: the client bundle is the loader's lazy-CJS factory artifact and the in-repo tsdown preset is not published — but community plugins show the format is simply a CJS file exporting `apply`/`inject` via `module.exports`, which our build emits directly (the official turtle-ui repo is another working external example); the bundle-purity gate rejects value imports across plugin packages (type-only imports are fine); the settings entry seam is a full settings section registered into the `settings.section` slot (`ctx.slots.inject` + `ctx.slots.register` with id/order/label/icon), the same seam built-in settings pages and community skill-manager plugins use — the `settings.plugin.item` card slot from the official cookbook targets plugin configuration cards inside the Plugins section, not standalone pages.
